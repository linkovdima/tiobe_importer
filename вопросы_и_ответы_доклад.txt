Вопросы к докладу и короткие ответы (репетиция)

1. Зачем онтология и RDF, а не обычная реляционная база?
Ответ: Связи «язык — свойство — публикация — фреймворк» естественно выражаются графом триплетов; проще наращивать схему и делать запросы с учётом отношений. Реляционная модель тоже возможна, но для семантического поиска и явных связей RDF удобнее; внутри можно использовать SPARQL.

2. Пользователь пишет SPARQL или только через веб-интерфейс?
Ответ: Основной сценарий — веб-интерфейс и фильтры без SPARQL. SPARQL используется на уровне реализации (запросы к графу), но не обязателен для конечного пользователя.

3. Откуда берутся данные и не нарушаете ли вы правила источников?
Ответ: Используются открытые API и общедоступные данные (TIOBE, GitHub API, Stack Overflow и др.). Соблюдаются лимиты запросов, условия использования сервисов и лицензии сторонних библиотек; секреты (токены) не хранятся в открытом репозитории.

4. Что делаете, когда сайт меняет вёрстку или API падает?
Ответ: Предусмотрены режимы однократного и тестового обновления, расписание, fallback (резервный сценарий, повтор, опора на последний успешный снимок), журнал обновлений для диагностики.

5. Как у вас устроен поиск и ранжирование?
Ответ: Запрос обрабатывается по нескольким типам сущностей (языки, публикации, фреймворки), результаты объединяются, дубликаты убираются, выдача ранжируется по релевантности; дополнительно работают фильтры по атрибутам.

6. Чем ваш сервис лучше DBpedia или Semantic Scholar?
Ответ: Это не замена глобальным системам, а предметно ориентированный сервис под языки программирования и учебный сценарий: своя схема, свои источники метрик, единый цикл импорт — поиск — сохранение — BibTeX.

7. Как решаете противоречия между источниками (разные названия, разные цифры)?
Ответ: Нормализация к единой онтологии, явные правила сопоставления сущностей; при необходимости приоритет источника или хранение нескольких значений с указанием происхождения. В перспективе — более формальная политика согласования данных.

8. Храните ли вы персональные данные? Как защищён личный кабинет?
Ответ: Личный кабинет подразумевает учётную запись; пароли должны храниться в виде хешей, доступ — через сессии. Объём ПДн минимален для учебного прототипа; при развёртывании в продакшене нужна политика конфиденциальности и соответствие 152-ФЗ.

9. Как масштабируется система при росте графа?
Ответ: Для ВКР достаточно файла Turtle и загрузки в память; при масштабировании логичен переход на triplestore, кэширование, индексация полнотекста, пагинация (у вас уже есть постраничный вывод).

10. Какие главные ограничения прототипа?
Ответ: Зависимость от внешних API и вёрстки, необходимость сопровождения парсеров, неполнота данных на раннем этапе по сравнению с крупными графами, задачи производительности при сильном росте данных.

11. Что планируете улучшить в первую очередь?
Ответ: Расширение онтологии, устойчивость парсинга, политика согласования источников, интеграция с LMS и каталогами литературы, рекомендации при слабой выдаче, версионирование онтологии.

12. Почему Flask, а не Django / FastAPI?
Ответ: Flask достаточен для прототипа: маршруты, шаблоны, REST API, интеграция с RDFLib и модулями проекта; выбор можно обосновать простотой и скоростью разработки учебного веб-слоя.
